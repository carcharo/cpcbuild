# Chapter 4: The player sprite

**Goal.** Put the lamplighter on the screen, make him walk left and right, and do it without
redrawing the room.

**What you'll learn**

- What a masked sprite is and how to import one (or draw one) in Studio.
- How to draw a sprite over a tiled background and erase it again with one call, `TileRestore`.
- Why the game redraws right after the screen's flyback, and what "single-buffered" means.
- How a sprite slot works, so that chapter 6 can add enemies without changing the layer.

**Time:** about 40 minutes.

**Before you start.** Chapter 3 is working. Copy `sprites.png` from `games/lamplighter/assets/` to
`assets/sprites.png`.

---

## Step 1: Meet the sprite sheet

A **sprite** is a picture that moves. Lamplighter's player and enemies are all in one PNG,
`sprites.png`: 96 x 16 pixels, **12 frames of 8 x 16 pixels** side by side. The frames, numbered from
the left:

| Frames | Picture |
|---|---|
| 0, 1, 2, 3 | the player facing right: stand, walk 1, walk 2, jump |
| 4, 5, 6, 7 | the same facing left |
| 8, 9 | climbing (two frames) |
| 10, 11 | the enemy (two frames of animation) |

(From `assets/make_art.py:11-16` and `game.bas:46-49`.) The background of the sheet is transparent
(alpha 0): that is what will let the room show through.

On screen a sprite is 8 mode-0 pixels wide, which is only 4 screen bytes (2 pixels per byte), and 16 lines
tall. The CPC library measures sprites in **bytes wide by lines tall**, so ours is **4 x 16**
(library: **Coordinates**).

### Masked sprites

A transparent pixel cannot just be pen 0: that would paint a black box round the player. A
**masked** sprite stores two bytes for every screen byte, a *mask* and the *pixels*. Drawing does
`screen = (screen AND mask) OR pixels`: where the mask bit is 1 the background shows through, where
it is 0 the sprite's pixel replaces it (library: **Data formats**, "Masked sprite"). So a 4 x 16
masked frame is 4 x 16 x 2 = **128 bytes**.

## Step 2: Import the frames

(Drawing your own sheet: the [art guide](../art-guide.md) covers frame layout and colours, and the
Aseprite extension in `tools/aseprite` sets it up for you.)

1. **CPCBuild: Import Image**, choose `assets/sprites.png`. The importer opens on a new
   `assets/sprites.cpcimp`.
2. Set:

| Section | Option | Value |
|---|---|---|
| Target | (the four buttons) | **CPC** |
| Target | mode buttons | **Mode 0** |
| Target | Name | `sprites` |
| Target | Output file | `assets/sprites.bas` |
| Sprites and tiles | (two buttons) | **Sprite** |
| Sprites and tiles | Frame size (WxH pixels) | `8x16` |
| Sprites and tiles | Masked (mask byte before each pixel byte) | ticked |
| Colours | Palette: Automatic / Pens / File | **File**, `assets/lamp.cpcpal` |
| Colours | Emit the palette (NAME_pal, NAME_PENS) | **off** |

   Emit the palette is off because the tiles already provide the palette (`tiles_pal`); the sprites share
   the same 16 pens, and only one copy is needed. The **Source** and **CPC result** previews show what the
   CPC will show (the result is cut into numbered frames); the **Colour mapping** table lists which image
   colour went to which pen. There is no need to set a **Transparent colour**: the field's own help says that
   pixels with alpha below 128 are transparent, and `sprites.png` has alpha 0 for its background.

3. Check the **Command** line at the top of the editor. It should match what the finished game's
   `build_assets.sh` runs, in the order Studio always writes the flags:

```
python3 tools/img2cpc.py --mode 0 --name sprites --sprite --frame 8x16 --masked --palette-file assets/lamp.cpcpal --no-palette assets/sprites.png -o assets/sprites.bas
```

4. Save. If you prefer to write the recipe as text:

```json
{
  "format": "cpcimp",
  "version": 1,
  "source": "assets/sprites.png",
  "output": "assets/sprites.bas",
  "target": "cpc",
  "mode": 0,
  "name": "sprites",
  "kind": "sprite",
  "frame": "8x16",
  "masked": true,
  "palette": { "file": "assets/lamp.cpcpal" },
  "emitPalette": false
}
```

Open `assets/sprites.bas`. The header says what the tool made, and the end of the file has the
constants you will use:

```basic
' Generated by img2cpc.py --mode 0 --name sprites --sprite --frame 8x16 --masked ...
' Source: assets/sprites.png, 96x16 pixels, mode 0
' 12 frame(s) of 4 bytes x 16 lines, masked, 128 bytes each
' Do not edit; regenerate it from the source image (command above).

DIM sprites(1535) AS UBYTE => { _
    $FF, $00, $AA, $15, $55, $2A, $FF, $00, $FF, $00, $00, $3F, $00, $3F, $FF, $00, _
```

(`games/lamplighter/assets/sprites.bas:1-8`; the header there reads `--frame 8x16 --masked`, in Studio's
flag order.) `sprites_W` is 4, `sprites_H` 16, `sprites_FRAMES` 12, `sprites_SIZE`
128 (bytes per frame). Frame *n* starts at `n * 128` in the array. A transparent pixel is a mask
bit of 1 and a pixel bit of 0, as in the first bytes above (`$FF, $00`: all four pixels of that
byte are background).

### The other way: draw the frames in the sprite editor

Run **CPCBuild: New Sprite**, choose **Mode 0**, and save as `assets/hero.cpcspr`. The **CPCBuild
Sprite Editor** opens. In the right-hand panel, under **Sprite**, set **Frame width** to 8 and **Frame
height** to 16 (pixels), tick **Masked**; under **Palette** choose **Shared file...** and pick
`assets/lamp.cpcpal`; under **Output** set **Output file** to `assets/hero.bas` (relative to the
document).

- The frames live in a strip on the left. **Add frame** appends one, **Duplicate frame** starts the next
  walk step from the last, and the **Onion skin** button (`O`) shows the previous frame ghosted behind
  the one you are drawing. A **Preview** panel animates the frames (**Play all frames**, with a rate).
- Draw with the pencil (`B`) using the left and right mouse buttons for two pens (badges **L** and **R**
  on the pen strip). For a masked sprite the first slot in the strip, marked **T**, is **transparent**:
  paint with it to cut holes in the sprite.
- Make the left-facing frames by duplicating the right-facing ones and applying **Flip horizontally**
  (**H** in the toolbar, `Shift+H`).
- The status line tells you the size, for this sprite `8x16 px = 4 bytes wide`, `128 B/frame (masked)`,
  and the number of frames and the total.
- Save writes the `.bas` (if **generateOnSave** is on; the **Output** section says whether the file is up
  to date). The **Generate** button does it without saving, and **Insert Asset Use** (a button in the
  editor's title bar) writes the `#include` and a `PutSpriteMasked` call into the code editor that is open.

Frame order matters because the game looks frames up by number: keep the table above.

## Step 3: Understand single-buffering

A CPC game normally has two choices for animation:

- **Double buffering**: draw the next frame in a hidden screen and flip. Smooth, but it reserves
  the 16 KB at &4000 for the hidden screen, so your code and data must fit in 12 KB (library:
  **Double buffering** and **Performance tips**).
- **Single buffering**: draw straight on the screen being shown. Cheaper in memory, but you can
  see half-drawn things unless you are careful.

Lamplighter is single-buffered on the 464, so it can use all the memory. The trick to keep it clean:

1. Draw at a fixed point in each frame, **right after the screen's flyback**, when the video beam
   is at the top and has the longest distance to go before it catches up with a sprite lower
   down.
2. Draw only what changed.
3. Erase a sprite by redrawing the background tiles under it, not by saving and restoring pixels.

Point 3 is `TileRestore(map, mapw, x, y, w, h)`: it redraws every tile that a screen rectangle
touches, taking the tile numbers from a map laid out from screen cell (0, 0) (library:
**Tiles**). One call erases a sprite: `TileRestore(room, 20, x, y, 4, 16)`. That is why chapter 3
put each room in a 20-wide array of its own.

## Step 4: The platform layer draws sprites

Replace `platform_cpc.bas`. It is the chapter 3 file with sprites, a new `PlatFrameEnd`
(which takes over from `PlatWait`) and a few arrays. Read it through before typing; the comments
explain each part.

```basic
' platform_cpc.bas -- the CPC side: screen, palette, tiles, text, keys (mode 0).
#include <cpc.bas>
#include <cpcbuild.bas>
#include <framehook.bas>
#include "assets/tiles.bas"
#include "assets/sprites.bas"
#include "assets/fontcpc.bas"

CONST NSLOT AS UBYTE = 5                ' sprite slots: 0 the player, 1-4 the enemies later
DIM blankPal(15) AS UBYTE            ' sixteen zeros: every pen black
DIM roomAddr AS UINTEGER             ' the room's tiles, for TileRestore
DIM sNF(4) AS UBYTE      ' frame to be drawn (255: none)
DIM sNX(4) AS UBYTE
DIM sNY(4) AS UBYTE
DIM sOF(4) AS UBYTE      ' frame drawn now (255: nothing)
DIM sOX(4) AS UBYTE
DIM sOY(4) AS UBYTE
DIM fT AS UINTEGER                   ' Frames() at the start of this step

SUB PlatInit()
  DIM i AS UBYTE
  Mode 0
  SetPalette(@tiles_pal(0), tiles_PENS)
  SetBorder 0
  ScreenInit()
  ClearScreen(0)
  SetTileSet(@tiles(0))
  TextFont(@font(0), font_FIRST, 7, font_FIRST + font_COUNT - 1)
  TextPen(7, 0)
  FOR i = 0 TO 4
    sNF(i) = 255
    sOF(i) = 255
  NEXT i
  GameMode(1)
END SUB

' Draws a room: the screen is blanked (all pens black) while the tiles go
' down, then the palette comes back.
SUB PlatRoom(addr AS UINTEGER)
  DIM i AS UBYTE
  roomAddr = addr
  SetPalette(@blankPal(0), 16)
  TileMap(addr, 0, 0, 20, 23)
  SetPalette(@tiles_pal(0), 16)
  FOR i = 0 TO 4
    sOF(i) = 255                 ' the room has just covered every sprite
  NEXT i
END SUB

' Sprite slot s shows frame f at pixel x, line y at the next flush.
SUB PlatSprite(s AS UBYTE, f AS UBYTE, x AS UBYTE, y AS UBYTE)
  sNF(s) = f
  sNX(s) = x
  sNY(s) = y
END SUB

' End of a step: wait until two frames have passed since the last one (25
' steps a second), then erase every sprite that was drawn and draw the new ones.
SUB PlatFrameEnd()
  DIM s AS UBYTE
  DO WHILE CAST(UINTEGER, Frames()) - fT < 2
  LOOP
  fT = CAST(UINTEGER, Frames())
  FOR s = 0 TO NSLOT - 1
    IF sOF(s) <> 255 THEN TileRestore(roomAddr, 20, sOX(s) >> 1, sOY(s), 4, 16)
  NEXT s
  FOR s = 0 TO NSLOT - 1
    IF sNF(s) <> 255 THEN
      PutSpriteMasked(sNX(s) >> 1, sNY(s), 4, 16, @sprites(CAST(UINTEGER, sNF(s)) << 7))
    END IF
    sOF(s) = sNF(s)
    sOX(s) = sNX(s)
    sOY(s) = sNY(s)
  NEXT s
END SUB

SUB PlatText(col AS UBYTE, row AS UBYTE, s AS STRING)
  TextAt(col, row, s)
END SUB

' Bits: 1 left (O, cursor left, joystick), 2 right (P, cursor right), 4 fire
' (Space, joystick fire), 8 any key, 16 up (Q), 32 down (A).
FUNCTION PlatInput() AS UBYTE
  DIM r AS UBYTE
  ScanKeys()
  r = 0
  IF KeyDown(KEY_O) <> 0 OR KeyDown(KEY_LEFT) <> 0 OR KeyDown(JOY_LEFT) <> 0 THEN r = 1
  IF KeyDown(KEY_P) <> 0 OR KeyDown(KEY_RIGHT) <> 0 OR KeyDown(JOY_RIGHT) <> 0 THEN r = r BOR 2
  IF KeyDown(KEY_SPACE) <> 0 OR KeyDown(JOY_FIRE1) <> 0 THEN r = r BOR 4
  IF KeyDown(KEY_Q) <> 0 OR KeyDown(KEY_UP) <> 0 OR KeyDown(JOY_UP) <> 0 THEN r = r BOR 16
  IF KeyDown(KEY_A) <> 0 OR KeyDown(KEY_DOWN) <> 0 OR KeyDown(JOY_DOWN) <> 0 THEN r = r BOR 32
  IF AnyKeyDown() <> 0 THEN r = r BOR 8
  RETURN r
END FUNCTION

FUNCTION PlatQuit() AS UBYTE
  RETURN KeyDown(KEY_ESC)
END FUNCTION
```

(Simplified from `platform_cpc.bas:110-224, 284-316`. The real `PlatSprite` and `PlatFlush` only
redraw sprites that moved or changed frame, and `PlatFlush` has an overlap rule: we add both in
chapter 6. This version erases and redraws every sprite every step.)

A few lines worth a second look:

- `sprites(CAST(UINTEGER, sNF(s)) << 7)`: frame number times 128, as a 16-bit number (a `UBYTE` would
  overflow at frame 2). `@sprites(...)` is the *address* of that element.
- `sNX(s) >> 1`: the game keeps x in **pixels** (0 to 159), the library wants **bytes**, 2 pixels each.
  That also means the player always moves in whole bytes, so the sprite never needs pre-shifting.
- `255` as a frame number means "no sprite in this slot", both for "to be drawn" and "drawn now".
- `GameMode(1)` and `Frames()` are explained below.

## Step 5: The game moves the player

Replace `game.bas`:

```basic
' game.bas -- the game logic: no drawing, only calls into the platform layer.
#include once "assets/rooms.bas"

CONST I_LEFT AS UBYTE = 1
CONST I_RIGHT AS UBYTE = 2

DIM cur(459) AS UBYTE                 ' the current room's tiles
DIM pRoom AS UBYTE
DIM pX, pY, pFace, pAnim, pMove AS UBYTE    ' x in pixels (even), y in lines
DIM startC, startR AS UBYTE

' Finds the room's start cell in the object list (record type 1).
SUB FindStart(id AS UBYTE)
  DIM o AS UINTEGER
  o = roff(id)
  DO WHILE robj(o) <> 0
    IF robj(o) = 1 THEN
      startC = robj(o + 1)
      startR = robj(o + 2)
    END IF
    o = o + 5
  LOOP
END SUB

SUB EnterRoom(id AS UBYTE)
  DIM base, i AS UINTEGER
  pRoom = id
  base = CAST(UINTEGER, id) * ROOM_SIZE
  FOR i = 0 TO ROOM_SIZE - 1
    cur(i) = rooms(base + i)
  NEXT i
  FindStart(id)
  pX = startC << 3                     ' cells to pixels
  pY = startR << 3
  PlatRoom(@cur(0))
END SUB

' One logic step: walk left or right two pixels (no gravity yet).
SUB GameStep(inp AS UBYTE)
  pMove = 0
  IF (inp BAND I_LEFT) <> 0 AND pX >= 2 THEN
    pX = pX - 2
    pFace = 1
    pMove = 1
  ELSEIF (inp BAND I_RIGHT) <> 0 AND pX < 150 THEN
    pX = pX + 2
    pFace = 0
    pMove = 1
  END IF
  IF pMove <> 0 THEN pAnim = pAnim + 1
END SUB

' Hands the player to the platform layer: frame 0 stand, 1-2 walk, then +4 facing left.
SUB GameDraw()
  DIM f AS UBYTE
  IF pMove <> 0 THEN f = 1 + ((pAnim >> 1) BAND 1) ELSE f = 0
  PlatSprite(0, f + (pFace << 2), pX, pY)
END SUB

PlatInit()
EnterRoom(9)
DO
  GameStep(PlatInput())
  GameDraw()
  PlatFrameEnd()
LOOP UNTIL PlatQuit()
```

(`FindStart` is a cut-down `LoadRoom`, `game.bas:213-255`; `GameDraw` is the player part of
`game.bas:737-760`.) The structure is the one the finished game uses all the way: **a step reads
the input, `GameStep` changes the world, `GameDraw` hands pictures to the platform layer,
`PlatFrameEnd` waits and draws.**

Notice `pX` is even and moves by 2: with a 4-byte-wide sprite and bytes of 2 pixels, an odd pixel
would not exist.

## Build and run

**CPCBuild: Build and Run**. Room 9 appears with the lamplighter standing at its left end, on the
floor. Press `P` (or the right cursor key) and he walks right, legs animating; `O` walks left,
facing left. He leaves no trail: the background is restored behind him. He walks through ledges,
lamps and walls (there is no collision yet), and stops at the room's edges. `ESC` quits.

The finished game's [walking picture](../../games/lamplighter/tests/golden/464/walk.png) shows the
same sprite mid-stride, with the HUD and an enemy added.

If the player leaves bits of himself behind, `TileRestore` is erasing the wrong rectangle: check
that `PlatRoom` stores `roomAddr = addr`. If you see black boxes around him, the sprite was imported
without **Masked**.

## How it works

**`PutSpriteMasked(x, y, w, h, spr)`** draws a masked sprite at byte column `x`, line `y`
(**Sprites**). Here `w` is 4 and `h` 16. The library's figure for a 4 x 16 sprite that is not clipped
is **5,283 T-states** (a frame is 80,000), so drawing is cheap; the BASIC call around it adds
roughly another 700.

**`TileRestore`** does the erasing, taking bytes and lines like a sprite does. A sprite that is not
aligned to a tile covers up to 2 x 3 = 6 cells, which costs about 9,600 T-states;
together with the draw, one moved sprite costs about 26,000 T-states
including the BASIC overhead. That number matters in chapter 9.

**`Frames()` and `GameMode(1)`.** The CPC's firmware runs an interrupt handler that eats about
12 % of the processor. `GameMode(1)` stops it outside firmware calls and gives you
the time back, but also stops the firmware's clock; so the library offers `Frames()`, a counter that
goes up once per frame (50 times a second), kept by the frame hook (library: **Frame hook and game
mode**). `PlatFrameEnd` waits until it has advanced by 2: that makes **25 logic steps a second**,
whatever the machine is doing. The same file also runs the music from the frame hook (chapter 8).

**Draw straight after the wait.** The loop erases and draws only after `Frames()` ticks over, i.e.
just after the flyback begins. In the real file this is spelled out: "a sprite that moved is erased
by TileRestore over its old rectangle ... and redrawn masked at the new place, all after the frame
wait of PlatFrameEnd, so the flicker is confined to the top of the beam's way"
(`platform_cpc.bas:16-19`). A sprite near the top of the screen can still flicker if the beam is
already there; that is the price of single buffering.

**The order of drawing.** The design sketched sorting the objects by y and drawing them top to
bottom, so each sprite is finished before the beam reaches it. The game as built does *not* sort. Look at
the real `PlatFlush` (`platform_cpc.bas:180-224`): it goes through the slots in slot order, 0 to 4 (the
player first, then the enemies), *twice*: first it erases every slot that is dirty (`TileRestore`), then it
draws every dirty slot (`PutSpriteMasked`). Because all of it happens right after the frame wait, when the
beam is at the top, a sprite low on the screen is drawn long before the beam gets there whatever its slot;
the order only matters for sprites that overlap, and the overlap rule of chapter 6 covers the one case
that needs it. The version in this chapter has the same order, with no dirty test.

**Slots.** `PlatSprite(slot, frame, x, y)` only *notes* what slot should show. `PlatFrameEnd` does
the work. Having the game say "what" and the layer say "how" is what makes the Plus build in chapter
11 possible: its `PlatSprite` hands the same notes to hardware sprites instead.

## Try this

1. Remove the `TileRestore` line. Walk. What happens? Put it back.
2. Make the player move 4 pixels a step instead of 2. What goes wrong with the frame
   numbers? (Hint: the walking frame uses `pAnim >> 1`.)
3. Change the frame wait from 2 to 1 (`< 1`). The game is twice as fast. Does it still look clean?
4. Draw a sixth frame in the sprite editor (or edit `sprites.png`), re-import, and show it in `GameDraw`.
5. Show a second sprite in slot 1 (`PlatSprite(1, 10, 100, 160)` in `GameDraw`): an enemy frame
   standing still. Walk the player past it. This version erases and redraws every sprite on every
   step, even one that has not moved: chapter 6 stops that, and chapter 9 measures why it matters.
